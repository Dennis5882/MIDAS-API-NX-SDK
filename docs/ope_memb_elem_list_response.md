`AELEM`을 쓰는 엔드포인트는 따로 있습니다 — **`/db/MEMB` (Design Member

SDK도 두 엔드포인트를 각각 다른 키로 구현하고 있습니다

`midas_nx.db.design` → `AELEM`).

## 2. 확인 과정에서 나온 별개 오타 — `"SELETION_TYPE"`

원문 Specifications 표 **2행의 Key가 `"SELETION_TYPE"`** 입니다. C가 빠져

우리 벤더드 매뉴얼은 이미 정상 철자로 정규화해 두었기 때문에 지금까지 아무도
보지 못한 항목입니다. 제보 대상으로는 이쪽이 실재하는 결함입니다.

## 3. 실측 재검증 — 요청하신 5개 항목 전부, 두 제품에서

**2026-09-06에 다시 돌렸습니다.** 지난 기록의 공백을 지적하신 게 맞아서, 답을
재구성하지 않고 새로 측정했습니다.

**방법.** 두 제품 각각 고유 키(`MIDAS_MAPI_KEY_GEN` / `MIDAS_MAPI_KEY_CIVIL`)로
`verify_connection()`을 찍어 `program`이 실제로 갈리는지 확인하고, `GET /db/NODE`
· `/db/ELEM` · `/db/MEMB`가 모두 `{"message": ""}`인 것을 확인한 뒤 시작했습니다.
**프로브 하나마다 `/doc/NEW`로 초기화하고 빈 것을 확인한 다음 더미 모델을 다시
세웠습니다** — 앞 프로브가 남긴 부재가 다음 프로브 결과를 오염시키지 않도록.
더미 모델은 `schema/live-cases.json`의 base model 페이로드를 그대로 재생한
것이고, 요소 2·3은 Z=3.2에 나란히 놓인 수평 보 두 개입니다. 프로브 본문은 원문
Request Example에 요소 번호만 이 모델에 맞게 바꾼 것입니다.

**결과는 Gen NX와 Civil NX가 완전히 동일합니다.**

| # | 보낸 것 | POST | 응답 본문 | 직후 `GET /db/MEMB` |
| --- | --- | --- | --- | --- |
| A | `ELEM_LIST: [2,3]`, `SELECTION` | **200** | `{"MEMB": {"1": {"AELEM": [2,3], "bREVERSE": false}}}` | 부재 1 생성됨 |
| B | `AELEM: [2,3]`, `SELECTION` | **200** | `{"error": {"message": "There is no valid element information."}}` | `{"message": ""}` — **생성 안 됨** |
| C | `ELEM_LIST: [2]` + `AELEM: [3]` 동시 | **200** | `{"MEMB": {"1": {"AELEM": [2], ...}}}` | 부재 = `[2]` |
| D | `AELEM: [2,3]`, `AUTO`/`ALL` | **200** | `{"1": {"AELEM": [1]}, "2": {"AELEM": [2,3]}}` | 모델 전체가 자동 배정됨 |
| E | 요소 목록 **없음**, `SELECTION` | **200** | `{"error": {"message": "There is no valid element information."}}` | `{"message": ""}` |

질문 항목별로:

1. **`SELECTION_TYPE` 값** — A·B·C·E는 모두 `"SELECTION"`입니다. 지적하신 `"ALL"`
   조건은 D로 따로 확인했습니다. `ALL`에서는 요소 목록이 무시되는 게 맞지만,
   **그 무시는 `AELEM`만이 아니라 `ELEM_LIST`에도 똑같이 적용됩니다.** 즉 `ALL`은
   `AELEM`을 되살리는 조건이 아니라 어떤 목록도 안 보는 조건이라, 이 질문의
   가설로는 B의 실패를 설명하지 못합니다.
2. **`AELEM` 거부 시 상태 코드와 응답 전문** — **HTTP 200**입니다. 4xx가 아닙니다.
   본문은 위 표 그대로 `{"error": {"message": "There is no valid element
   information."}}` 이 전부이고, 다른 키는 없습니다. (이 API가 실패를 200으로
   돌려주는 사례는 이미 알려져 있고, 이번에 상태 코드까지 기록했습니다.)
3. **두 키를 동시에 보냈을 때** — C가 답입니다. 값이 겹치지 않게
   `ELEM_LIST: [2]` / `AELEM: [3]`으로 보냈더니 만들어진 부재는 **`[2]`** 였습니다.
   **`ELEM_LIST`가 채택되고 `AELEM`은 통째로 무시됩니다.** 충돌도, 경고도
   없습니다.
4. **테스트한 제품 빌드** — API에 빌드를 알려주는 엔드포인트가 없어서 이 값만은
   프로그램에서 읽을 수 없습니다. 세션은 `verify_connection()` 기준 각각
   `program: "gen"` / `program: "civil"`이고, 두 키가 서로 다른 제품에 붙은 것을
   확인했습니다. 빌드 문자열은 저자가 제품 화면에서 읽어 채워야 합니다.
5. **성공 시 응답이 `AELEM`으로 돌아오는지** — 네. POST 응답도 `GET /db/MEMB`도
   모두 `AELEM`입니다. **요청은 `ELEM_LIST`, 응답·저장 레코드는 `AELEM`** 이라는
   원문 서술 그대로입니다.

### 결정적인 부분은 B와 E가 같다는 점입니다

`AELEM`을 보냈을 때(B)와 **요소 목록을 아예 안 보냈을 때**(E)의 응답이 상태
코드와 메시지까지 완전히 같습니다. 즉 서버 입장에서 `AELEM`을 보내는 것은
**아무것도 안 보내는 것과 구별되지 않습니다.** 요청 본문에서 그 키는 읽히지
않습니다. 이건 "값이 잘못됐다"가 아니라 "그 키가 요청 스키마에 없다"의 신호입니다.

### 덤으로 나온 두 가지

- **`bREVERSE`가 POST 응답과 GET 응답에서 다릅니다.** 성공한 프로브 3개 모두,
  두 제품 모두에서 POST 응답은 `"bREVERSE": false`인데 직후 `GET /db/MEMB`는
  같은 부재를 `"bREVERSE": true`로 돌려줍니다. **POST 응답 본문을 저장된
  레코드로 믿으면 안 된다**는 뜻이라 별건으로 기록해 두었습니다.
- **`POST /doc/NEW`를 본문 없이 호출하면 HTTP 500** `{"error": {"message":
  "Cannot read properties of null (reading 'Argument')"}}` 이고 문서는 초기화되지
  않습니다. `{"Argument": {}}`를 실어야 `200 "... command complete"`와 함께 실제로
  비워집니다. 첫 시도에서 이걸 무시하고 지나가는 바람에 프로브들이 누적된 모델
  위에서 돌았고, 그래서 전부 폐기하고 프로브마다 초기화를 검증하는 방식으로 다시
  돌렸습니다. 위 표는 다시 돌린 쪽 결과입니다.

**두 세션은 빈 문서 상태로 정리했고, 정리 후 `GET /db/NODE` · `/db/ELEM` ·
`/db/MEMB`가 모두 `{"message": ""}`임을 확인했습니다.**

## 4. Jira 제보(A-7)에 대한 의견

요청서의 걱정 방향은 정확했는데, 결론이 반대입니다.

현재 제보는 **"표의 `ELEM_LIST`를 `AELEM`으로 고쳐달라"** 인데, 표는 지금
맞습니다. 요청 예제도 맞습니다. 요청서가 대안으로 제시한 **"표가 아니라 예제를
고치자"** 도 성립하지 않습니다 — 요청 예제는 이미 `ELEM_LIST`이기 때문입니다.

요청 키에 관해서는 **고칠 것이 없습니다.** 요청은 `ELEM_LIST`, 응답은 `AELEM`이고,
원문 세 곳이 그 상태로 서로 일관됩니다. 요청/응답 필드명이 다른 것은 이 API에서
드물지 않고, 이 아티클은 그걸 그대로 보여주고 있을 뿐입니다.

그래서 제안은:

1. **A-7은 철회**하는 쪽이 맞다고 봅니다. 지금 상태로 반영되면 표가 실제 API와
   어긋나게 됩니다.
2. 굳이 이 아티클에 대해 제보를 남긴다면 **`"SELETION_TYPE"` 오타** 쪽이
   실재하는 항목입니다.
3. 요청/응답 키가 다르다는 점은 결함이 아니라 문서 명확성 문제이므로, 필요하면
   별건으로 "요청 키와 응답 키가 다름을 본문에 명시해달라" 정도가 적절합니다.

**Jira는 저희가 손대지 않습니다.** 이 저장소의 규칙상 저자의 명시적 지시 없이는
MAPI 이슈를 생성하거나 편집하지 않습니다. 위 내용은 판단 재료로만 전달합니다.
